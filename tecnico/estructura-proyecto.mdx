El repositorio del Gestor de Pruebas para Llamados tiene una estructura deliberadamente plana: no hay paso de compilación, no hay carpetas `src/` ni `dist/`, y cada archivo cumple una responsabilidad única y bien delimitada. Entender qué hace cada pieza y en qué orden se carga es fundamental para realizar cualquier modificación sin romper el contrato de variables globales del que depende la aplicación.

---

## Árbol de archivos

```text
gestor_pruebas_llamados/
│
├── index.html                  # Pantalla del Generador de Evaluaciones
├── admin.html                  # Panel de Administración (ABM)
│
├── js/
│   ├── interfaz.js             # Lógica del generador: selección de cargos,
│   │                           #   dinámicas, tiempos y generación del informe
│   ├── informe.js              # Constructores HTML del informe y hojas de trabajo
│   ├── administracion.js       # Lógica ABM: altas, ediciones, bajas y asistente IA
│   └── utilidades.js           # Funciones compartidas: esc(), bonito(), etc.
│
├── estilos/
│   ├── aplicacion.css          # Estilos del generador + reglas de impresión A4
│   ├── administracion.css      # Estilos del panel de administración
│   └── informe.css             # Estilos del informe y hojas del postulante
│
├── datos/
│   └── datos.js                # Capa de datos: objeto Datos con cargar(),
│                               #   guardar(), listarInformes(), leerInforme(),
│                               #   guardarInforme()
│
├── netlify/
│   └── functions/
│       └── pruebas.js          # Función serverless: puente entre el navegador
│                               #   y la API de GitHub (repositorio bd)
│
└── netlify.toml                # Configuración de despliegue en Netlify
```

## Descripción detallada de cada archivo

### Páginas HTML

<AccordionGroup>
  <Accordion title="index.html — Pantalla del Generador">
    Punto de entrada principal de la aplicación. Contiene el panel de control (selector de área y cargo, casillas de dinámicas, cantidad de postulantes, botón **Generar**) y el área imprimible donde se vuelca el informe generado.

    Carga los scripts en este orden fijo: `js/utilidades.js` → `datos/datos.js` → `js/informe.js` → `js/interfaz.js`. El orden importa: cada script puede depender de los globales que expongan los anteriores.

    Las reglas CSS de impresión (`@page`, `print-color-adjust: exact`, saltos de página por `.candidate-sheet`) están definidas en `estilos/aplicacion.css`, que también se carga desde esta página.
  </Accordion>

  <Accordion title="admin.html — Panel de Administración">
    Pantalla de gestión del catálogo. Contiene los modales para crear y editar áreas, cargos y dinámicas, el botón **Guardar en GitHub** y el asistente de IA integrado en el mismo panel.

    Carga: `js/utilidades.js` → `datos/datos.js` → `js/administracion.js`. No carga `js/informe.js`.

    <Warning>
      Todos los cambios realizados en esta pantalla se mantienen únicamente en memoria. Si la página se recarga sin haber presionado **Guardar en GitHub**, los cambios se pierden de forma permanente.
    </Warning>
  </Accordion>
</AccordionGroup>

### Scripts JavaScript

<AccordionGroup>
  <Accordion title="js/interfaz.js — Lógica del Generador">
    Núcleo funcional de la pantalla principal. Sus responsabilidades son:

    - Al cargar la página, llama a `Datos.cargar()` y guarda el resultado en la variable local `D` (`{ areas, cargos, dinamicas }`).
    - Rellena los selectores de área y cargo a partir de los datos cargados.
    - Al cambiar el cargo, filtra `dinamicas` por `cargo_id` y muestra las casillas correspondientes.
    - Calcula el tiempo total estimado sumando los minutos de las dinámicas marcadas.
    - Al presionar **Generar**, construye el HTML completo del informe llamando a funciones de `informe.js`.
    - Implementa `limpiarResultados()`, que borra el informe si se cambia la selección para evitar datos mezclados.

    **Expone:** `D` (objeto local con `areas`, `cargos`, `dinamicas`).
    **Consume:** `Datos` (de `datos/datos.js`), funciones de `informe.js`, `esc()` y `bonito()` de `utilidades.js`.
  </Accordion>

  <Accordion title="js/informe.js — Constructores del informe">
    Contiene las funciones que convierten los datos en HTML imprimible. Entre ellas:

    - Construcción del bloque de cada dinámica (título, código, descripción, tiempo, guía de observación, corrector).
    - Generación de la tabla de puntaje por postulante (filas = dinámicas, columnas = competencias, escala 0–5).
    - Generación de las hojas de trabajo del postulante (consigna, renglones de respuesta, espacio para nombre y fecha).
    - Aplicación del interruptor **Guía y corrector** mediante la clase CSS `ocultar-guia`.

    **Expone:** funciones de construcción HTML (consumidas por `interfaz.js`).
    **Consume:** los datos que le pasa `interfaz.js` como parámetros, `esc()` de `utilidades.js`.
  </Accordion>

  <Accordion title="js/administracion.js — Lógica del Panel ABM y asistente IA">
    Gestiona el ciclo de vida completo del catálogo en memoria y aloja el asistente **Directrices desde bases (IA)**:

    - **Altas:** `guardarArea()`, `guardarCargo()`, `guardarDinamica()` con generación automática de códigos (`CAR-<área>-<esp>-<NN>`, `DIN-<área>-<esp>-<NN>`).
    - **Edición:** `editarDinamica()` — el código no cambia al editar.
    - **Baja lógica:** `eliminarDinamica()` con confirmación; los elementos eliminados se marcan `activo: false`.
    - **Exportación:** llama a `Datos.guardar()` para escribir los tres JSON en el repositorio `bd` vía la Netlify Function.
    - **Asistente IA:** carga **Mammoth.js 1.6.0** desde `cdnjs.cloudflare.com` (constante `MAMMOTH` al inicio del archivo) únicamente cuando el usuario activa el asistente. Extrae el texto de un `.docx` íntegramente en el navegador (el archivo no se sube a ningún servidor), anonimiza datos sensibles y genera un prompt para copiar a una IA externa.

    Notas importantes sobre las operaciones **no disponibles** desde la interfaz: modificar o eliminar áreas y cargos existentes requiere editar los archivos JSON a mano en el repositorio `bd`.

    **Expone:** funciones del ABM accesibles desde los eventos del HTML.
    **Consume:** `Datos` (de `datos/datos.js`), `esc()` y `bonito()` de `utilidades.js`.

    <Note>
      Para cambiar la URL de Mammoth (por ejemplo, para usar una copia local), modifique únicamente la constante `MAMMOTH` al comienzo de `js/administracion.js`. No es necesario tocar ningún otro archivo.
    </Note>
  </Accordion>

  <Accordion title="js/utilidades.js — Funciones compartidas">
    Biblioteca de funciones de propósito general usadas por los demás scripts:

    - `esc(texto)` — Escapa caracteres especiales HTML (`<`, `>`, `"`, `&`) para evitar inyección de HTML al insertar datos del usuario en el DOM.
    - `bonito(nombre)` — Aplica capitalización «título» a un nombre para mostrarlo con formato consistente.
    - Funciones auxiliares para la composición de hojas del postulante y el conteo de renglones de respuesta.

    **Expone:** `esc()`, `bonito()` y utilidades de composición.
    **Consume:** ninguna dependencia interna.
  </Accordion>
</AccordionGroup>

### Estilos CSS

<AccordionGroup>
  <Accordion title="estilos/aplicacion.css — Generador e impresión">
    Estilos visuales de `index.html` más todas las reglas de impresión:

    - `@page { size: A4; margin: 15mm }` para la hoja impresa.
    - `print-color-adjust: exact` para forzar la impresión de colores de fondo.
    - `.no-print` oculta el panel de control al imprimir.
    - `.candidate-sheet { page-break-before: always }` garantiza que cada hoja del postulante comience en una página nueva.
  </Accordion>

  <Accordion title="estilos/administracion.css — Panel de Administración">
    Estilos exclusivos de `admin.html`: layout de la lista de elementos, modales de creación y edición, indicadores de estado y botones de acción (editar, borrar, guardar).
  </Accordion>

  <Accordion title="estilos/informe.css — Informe y hojas del postulante">
    Estilos tipográficos y de tabla del informe generado: encabezados, bloques de dinámica, tabla de puntaje, recuadros de guía de observación y corrector, hojas del postulante con renglones de respuesta.

    La clase `.ocultar-guia` (aplicada por el interruptor **Guía y corrector**) oculta los bloques `.bloque-guia` tanto en pantalla como al imprimir.
  </Accordion>
</AccordionGroup>

### Capa de datos

<AccordionGroup>
  <Accordion title="datos/datos.js — Objeto Datos (cliente de la API)">
    Único punto de contacto entre el frontend y la Netlify Function. Expone el objeto global `Datos` con los siguientes métodos:

    | Método | Tipo | Descripción |
    |---|---|---|
    | `Datos.cargar()` | `async` | GET a `/.netlify/functions/pruebas`. Retorna `{ areas, cargos, dinamicas }`. |
    | `Datos.guardar(base, claveIngresada)` | `async` | POST a `/.netlify/functions/pruebas`. Escribe los tres JSON en el repositorio `bd`. |
    | `Datos.listarInformes()` | `async` | GET del índice `informes.json`. Retorna el listado de informes guardados. |
    | `Datos.leerInforme(codigo)` | `async` | GET de `informes/<codigo>.json`. Retorna el informe completo. |
    | `Datos.guardarInforme(informe, opciones)` | `async` | POST que escribe el informe en `informes/` y actualiza el índice. |

    También expone el getter `Datos.origen`, que devuelve `'bd'` tras una carga o guardado exitoso.

    **Expone:** `Datos` (objeto global).
    **Consume:** ninguna dependencia interna; usa `fetch` nativo del navegador.
  </Accordion>
</AccordionGroup>

### Función serverless

<AccordionGroup>
  <Accordion title="netlify/functions/pruebas.js — API Bridge">
    Función serverless de Netlify que actúa como intermediario entre el navegador y la API REST de GitHub. Es el único componente del sistema que tiene acceso directo al token de GitHub y a la clave de administración.

    **Operaciones que implementa:**

    - `GET` sin parámetros → Lee `areas.json`, `cargos.json` y `dinamicas.json` del repositorio `bd` en paralelo y los devuelve combinados.
    - `GET` con parámetro de informe → Lee un informe individual o el índice de informes.
    - `POST` con datos → Valida la clave (`CLAVE_PRUEBAS`), luego escribe o actualiza los archivos en `bd` usando la API de contenidos de GitHub (incluyendo el SHA del archivo previo para actualizaciones).

    **Variables de entorno requeridas:**

    ```text
    GITHUB_TOKEN_PRUEBAS_LLAMADOS_BD   # Token de acceso a GitHub
    CLAVE_PRUEBAS                      # Contraseña para operaciones de escritura
    ```

    **Expone:** endpoint HTTP en `/.netlify/functions/pruebas`.
    **Consume:** API REST de GitHub (`api.github.com`), variables de entorno de Netlify.
  </Accordion>
</AccordionGroup>

### Configuración de despliegue

<AccordionGroup>
  <Accordion title="netlify.toml — Configuración de Netlify">
    Archivo de configuración declarativa para el despliegue en Netlify. No define ningún comando de build ni directorio de publicación alternativo (la raíz del repositorio se publica tal cual). Configura una redirección que devuelve `404` para cualquier petición a `/documentacion/*`, manteniendo esa carpeta inaccesible desde el exterior aunque exista en el repositorio.

    ```toml
    [[redirects]]
      from = "/documentacion/*"
      to = "/404.html"
      status = 404
      force = true
    ```
  </Accordion>
</AccordionGroup>

## Tabla de contratos de variables globales

Los scripts no usan módulos ES (`import`/`export`): comparten estado a través del objeto global `Datos` y de variables locales por pantalla. Modificar el orden de carga de scripts sin verificar estos contratos puede causar errores de referencia en tiempo de ejecución.

| Global | Expuesto por | Consumido por | Descripción |
|---|---|---|---|
| `Datos` | `datos/datos.js` | `js/interfaz.js`, `js/administracion.js` | Objeto con los métodos de acceso a la API. Debe cargarse antes que cualquier script que lo use. |
| `D` | `js/interfaz.js` (generador) | `js/informe.js` (a través de parámetros) | Contiene `{ areas, cargos, dinamicas }` una vez que `Datos.cargar()` resuelve. Variable local de cada pantalla: `interfaz.js` y `administracion.js` declaran su propia copia. |

<Warning>
  El orden de carga de scripts en el HTML no es negociable. En `index.html` el orden es: `js/utilidades.js` → `datos/datos.js` → `js/informe.js` → `js/interfaz.js`. En `admin.html`: `js/utilidades.js` → `datos/datos.js` → `js/administracion.js`. Si se reordena o se migra a un bundler, es imprescindible verificar que `Datos` esté disponible antes de que `interfaz.js` o `administracion.js` intenten usarlo.
</Warning>

## Cambios que requieren edición manual de JSON

Algunas operaciones no están disponibles desde la interfaz de administración y deben realizarse editando directamente los archivos en el repositorio `FABIOR1981/bd`:

<CardGroup cols={2}>
  <Card title="Competencias de un cargo" icon="list-check">
    Agregar, modificar o eliminar las competencias que definen las columnas de la tabla de puntaje. Se edita el arreglo `competencias` dentro del cargo correspondiente en `cargos.json`.
  </Card>
  <Card title="Renombrar o eliminar áreas y cargos" icon="pencil">
    El Panel de Administración solo permite crear nuevas áreas y cargos. Para renombrar o eliminar uno existente hay que editar `areas.json` o `cargos.json` a mano y, si se cambia un código de cargo, actualizar también el `cargo_id` de todas sus dinámicas en `dinamicas.json`.
  </Card>
  <Card title="Corregir el cargo_id de una dinámica" icon="link">
    Si una dinámica quedó asociada al cargo incorrecto, debe editarse su campo `cargo_id` en `dinamicas.json` para que coincida exactamente con la clave del cargo deseado en `cargos.json`.
  </Card>
  <Card title="Incorporar respuestas de la IA" icon="robot">
    Cuando la IA propone nuevas dinámicas en formato JSON, deben pegarse manualmente en los archivos correspondientes respetando la estructura: objetos en `areas.json` y `cargos.json`, elementos del arreglo en `dinamicas.json`.
  </Card>
</CardGroup>
